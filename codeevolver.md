## ARCHITECTURE TITLE: Hybrid ReAct — two-phase for count_pivot, exact hobby/occupation tools in Phase 1 (EntityFinderSig), DOB exact-match tool

## ARCHITECTURE SUMMARY:
The system is a DSPy-based question-answering pipeline that uses a hybrid dispatch strategy to answer multi-hop questions over PhantomWiki. The pipeline is organized into three layers: a pipeline wrapper (`PhantomWikiReActPipeline`) that owns infrastructure, a core reasoning module (`PhantomWikiReAct`) that CodeEvolver optimizes, and a metric module (`phantomwiki_f1_feedback`) that scores predictions against gold answers.

The key innovation is a hybrid approach that routes questions by type using deterministic Python-based classification (`_classify_question`). Questions are classified into four types — `entity`, `attribute`, `count_answer`, `count_pivot` — using pure lexical rules. For `count_pivot` questions, a two-phase strategy is used: Phase 1 (`EntityFinderSig` via `dspy.ReAct`, max_iters=40) finds all pivot entities using five tools: `search_wiki` (k=10), `search_wiki_broad` (k=50), `search_by_date_exact`, `search_by_hobby`, and `search_by_occupation`. The `search_by_hobby` and `search_by_occupation` tools use pre-built exact indexes to enumerate ALL matching persons — far more reliable than ColBERT semantic search. Phase 2 (`CountComputerSig`, max_iters=15) is called once per pivot entity to count independently, preventing fan-out collapse. Hobby/occupation anchors in `count_pivot` questions are also handled at the Python level in `forward()` for simple "does the person whose hobby/occupation is X" patterns (direct index lookup → pivot entities). For all other question types (`entity`, `attribute`, `count_answer`), a single-phase `PhantomWikiQA` ReAct (max_iters=50) is used with only three tools (no hobby/occupation exact tools). The LM is `openai/gpt-5.4-nano` with `reasoning_effort="low"`.

## ARCHITECTURE DESCRIPTION:
**What the program does:** Given a natural language question about fictional PhantomWiki entities, the system classifies it deterministically, then dispatches to a single-phase or two-phase ReAct strategy. For `count_pivot` questions the two-phase approach fixes multi-count fan-out collapse, and Phase 1 now has access to exact hobby/occupation index tools for complete anchor enumeration. For all other question types the single-phase `PhantomWikiQA` ReAct is used.

**Key modules and responsibilities:**

- `src/program/phantomwiki_pipeline.py` — `PhantomWikiReActPipeline` (the evaluator's entry point). Constructs the `CountingRM` retriever (wraps `dspy.ColBERTv2` pointed at `https://julianghadially--colbert-server-phantom-wiki-colbertserv-75bf93.modal.run/api/search`), the LM (`gpt-5.4-nano`, `reasoning_effort="low"`), and the `PhantomWikiReAct` module. Its `forward(question)` sets the LM and RM into DSPy's thread-local context and delegates to the module.

- `src/program/phantomwiki_module.py` — `PhantomWikiReAct` (the file CodeEvolver mutates). Contains three DSPy Signatures and the main module: `PhantomWikiQA` (single-phase, handles entity/attribute/count_answer questions), `EntityFinderSig` (two-phase Phase 1, finds all pivot entities for count_pivot questions; InputFields: `question`, `question_type`; OutputField: `target_entities`), and `CountComputerSig` (two-phase Phase 2, counts X for a single pivot entity). The module-level `_classify_question(question)` function deterministically routes questions. The single-phase `react` agent has three tools: `search_wiki` (k=10), `search_wiki_broad` (k=50), `search_by_date_exact`. Phase 1 `entity_finder` has five tools: `search_wiki`, `search_wiki_broad`, `search_by_date_exact`, `search_by_hobby`, and `search_by_occupation` — the latter two use pre-built exact indexes and return ALL matching persons for hobby/occupation anchors. `EntityFinderSig`'s docstring instructs the agent to FIRST call `search_by_occupation("X")` or `search_by_hobby("X")` before any ColBERT searches for occupation/hobby-anchored questions. For `count_pivot` questions with simple hobby/occupation anchors, `forward()` may bypass Phase 1 entirely with a direct index lookup. The Phase 2 entity cap is 30. `forward()` uses two-phase dispatch only for `count_pivot` (with single-phase fallback when Phase 1 finds nothing); all other types use single-phase directly.

- `src/program/counting_rm.py` — `CountingRM`. A `dspy.Retrieve` subclass that wraps any retriever, increments a call counter on each retrieval, monkey-patches the ColBERTv2 HTTP client to enforce a 60-second timeout, and retries up to 2 times on timeout/connection errors. Used to track retrieval cost per question.

- `src/metric/metric.py` — Two metrics: `phantomwiki_f1` (plain float F1 for the evaluation harness) and `phantomwiki_f1_feedback` (returns `dspy.teleprompt.gepa.ScoreWithFeedback` with score + human-readable breakdown of correct/missed/extra answers). Normalization is lowercase + strip; scoring is set-based precision/recall/F1 over answer lists.

**Data flow:** `evaluate.py` loads JSON question splits from `output/depth_10_size_1000000/`, calls `PhantomWikiReActPipeline.forward(question)` per row, and scores the returned `dspy.Prediction.answer` against the gold `answer` field using `phantomwiki_f1`. CodeEvolver uses `phantomwiki_f1_feedback` during optimization for richer gradient signal.

**Metric being optimized:** Token-level F1 between the predicted answer set and the gold answer set (both normalized to lowercase). A score of 1.0 requires exactly matching the complete set of correct answers — no more, no less.
